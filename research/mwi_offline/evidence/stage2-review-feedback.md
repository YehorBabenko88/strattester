## Findings requiring correction or qualification

### P1: development boundaries depend on outcome-selected full-history endpoints

feedback.py:13 builds all examples and15-17 derives development calendar boundaries from rows[0]/rows[-1], then applies fractions .40/.50/.58. Eligible rows exclude future AMBIGUOUS outcomes in features.py. Therefore changing an original-final-OOS future bar to make the last eligible episode ambiguous can remove that last row, alter span and move earlier training/calibration/development boundaries. The current code does not directly fit original final-OOS labels into the model, but the stronger claim that future outcomes cannot alter model selection/artifacts is not established and can fail through this endpoint dependency.

Fix: pre-register absolute calendar endpoints from an immutable source clock schedule, independent of eligible labels/outcomes and future values; use those same endpoint identities for both baseline original OOS and feedback development. Add an adversarial test changing future OHLC, including terminal episode ambiguity, while preserving clocks; require unchanged early fit IDs/models/temperatures. The current test_feedback.py:22-25 only asserts development_end < reserved_original_oos_start and all decision cutoffs before development_end; it does not test this invariance.

Also feedback.py:17 gives split_at evaluation_as_of=max availability across the whole input. evaluation.py:77-80 purges training/calibration by outcome end/availability but does not purge test labels at development_end. Thus the development_end field bounds test DECISIONS, not necessarily their outcome maturity. For complete synthetic minute data this early .58 test horizon is well separated from .80 OOS; for delayed observations the test may use labels that become available much later. Explicitly bind a development observation/label-maturity deadline and require every label_available <= that deadline before feedback. Keep original final OOS unused rather than allowing its receive clock to authorize development evidence.

### P1: completed resume may return an artifact whose pin is missing

feedback.py:64-68 validates only entries supplied in checkpoint.artifacts, then unconditionally reads result.json on COMPLETE. Removing the result.json entry (or clearing the artifact map) allows an altered result.json to bypass the hash check. This is a concrete missing-manifest-entry validation defect, not a requirement for cryptographic authenticity from a self-authored directory.

Fix: exact checkpoint schema/status validation, required config/model/result artifact inventory for COMPLETE, and result identity checks against config; reject missing mandatory pins and surplus/unrecognized checkpoint fields. Consider a separately held expected checkpoint hash when stronger tamper provenance is needed. Even with that inventory fix, an attacker rewriting BOTH artifact bytes and all matching pins in an unsigned checkpoint is outside a digest-only accidental-corruption guarantee; avoid claiming authenticated tamper-proof storage.

### P2: checkpoint persistence is not crash-atomic

feedback.py:76 writes a new artifact, then78 overwrites checkpoint.json directly; COMPLETE status is overwritten directly103. A process crash during checkpoint write may truncate the only checkpoint, making resume fail JSON parsing despite preserved immutable artifacts. The code can replay deterministic stages from a valid IN_PROGRESS checkpoint and refuses conflicting artifact bytes73-74, which is useful. It does not yet establish crash-consistent checkpoint/restart across every write boundary. Use a temp checkpoint plus atomic replace and durable flush policy appropriate to this standalone filesystem, and test interruption at checkpoint replacement, not only a simulation exception.

### P2: the 60-second budget is a cooperative pre-candidate check

feedback.py:84 checks elapsed time only before each candidate. development_fit80 and an individual base+stress pair86 may finish after the deadline without interruption. The6-candidate/two-version bounds are enforced by code and strategy validator(strategy.py:22, feedback.py:82-95); the wall budget is not a hard runtime quota. Resume resets monotonic start56-57 and replays stages; it does not preserve cumulative spent wall/CPU budget. resource report correctly says hard_cpu_quota=false. Describe bounded candidate count/cooperative deadline, or add an external approved execution budget and persisted consumption before claiming hard containment.
